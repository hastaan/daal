# Build the Iran client on sing-box, wrap natively, avoid Flutter

**The recommendation is unambiguous: Go as the core language, sing-box as the embedded engine, native Swift/Kotlin on mobile, and Tauri v2 with sing-box as a sidecar on desktop.** This is the only stack that satisfies the hard constraint "reimplementing is a non-starter" while keeping binaries compact and App Store / Play Store / sideload paths viable. Every other combination either loses half the required protocols or adds tens of megabytes of runtime overhead for a UI framework the user doesn't need. The backstory is simple — the circumvention-protocol world runs on Go. sing-box, Xray-core, v2ray-core, mihomo, Hysteria2, Trojan-Go, Psiphon, Snowflake, meek, obfs4, Cloak, and Lantern are all Go; most have no production-grade implementation in any other language. A Rust, C++, or Zig core would force you to reimplement VLESS/Reality-Vision, Hysteria2, Psiphon, Snowflake, obfs4, Cloak and Lantern from scratch — a two-year detour that defeats the purpose. The broader implication is that a new Iran client is not a language or framework problem; it is a **distribution, packaging, and bootstrap problem on top of a solved protocol stack**.

## Why Go wins the language fight decisively

Go is not the smallest, fastest, or safest of the four candidates. It wins purely on ecosystem coverage of circumvention protocols, which the task explicitly treats as the second highest priority and — on reflection — the real first-order constraint. **Sing-box alone ships Shadowsocks/SS2022, VMess, VLESS (with XTLS-Vision and Reality), Trojan, Hysteria/Hysteria2, TUIC, WireGuard userspace, ShadowTLS, AnyTLS, NaiveProxy outbound, SSH tunnel, Tor with obfs4/meek plugins, and ECH**, which covers roughly 14 of the ~18 protocols the brief asks for in a single, actively maintained Go library. Adding `psiphon-tunnel-core`, `snowflake`, `yawning/obfs4`, `cbeuw/Cloak`, and `getlantern/flashlight` as separate Go imports fills the rest. Every one of those projects has Go as its reference implementation; several exist in no other language.

Binary-size and startup numbers cost you something real for that coverage. A release sing-box v1.12.x Linux-amd64 binary lands around **15.8 MB** stripped, rising to **25–28 MB** for the extended build that compiles in VLESS, Reality, NaiveProxy, Hysteria2, TUIC, WireGuard-go, and gVisor TUN. Xray-core is ~18.8 MB; mihomo ~16–20 MB; Psiphon's ConsoleClient ~25–35 MB. Cold start is 50–150 ms on a modern desktop and 200–500 ms on ARM mobile, and steady-state RSS runs 30–80 MB idle. By contrast, `shadowsocks-rust` is ~5 MB and boots in 5–30 ms, `boringtun` is ~1.5 MB for WireGuard-only — but neither brings VLESS/Reality, Hysteria2, Psiphon, or Snowflake, and `leaf` (the most complete Rust multi-protocol proxy) explicitly overflows iOS's Network Extension memory limit with its default feature set and covers maybe half the required protocols. C/C++ offers fragmented leaf libraries (shadowsocks-libev, trojan, NaiveProxy, OpenVPN) with no cohesive multi-protocol engine. Zig has essentially no mature circumvention libraries at all.

The honest trade-off is that **you pay roughly 15–20 MB of binary weight to get a maintained, actively developed protocol stack that a hostile state adversary cannot easily defeat**. Iran's DPI apparatus targets specific fingerprints — VLESS-Reality, Hysteria2 obfuscation, uTLS behavior — that require frequent updates. Reimplementing these in Rust means you are one upstream patch behind, always. The 15 MB is cheap insurance.

Two narrow exceptions: WireGuard can be split out to **boringtun** (Rust, ~1.5 MB) if the iOS Network Extension memory ceiling becomes a problem — this is what Cloudflare WARP does. And for the C++-only NaiveProxy (Chromium net/), shell out or use sing-box's wrapper rather than reimplement. Zig is worth keeping as your `zig cc` cross-compilation driver for cgo builds, Uber-style, but never as the engine language.

## Which existing architecture to copy

The reference-project survey produced a clear ranking of architecture patterns, and one pattern matches our priorities almost exactly.

**Copy sing-box-for-apple's iOS pattern, NekoBox-for-Android's Android pattern, and Clash Verge Rev's desktop pattern.** All three build on the same Go core (sing-box itself, or mihomo, which is very close architecturally). None of them use Flutter for the UI.

The SagerNet reference clients — **SFI** (iOS), **SFM** (macOS), **SFT** (tvOS), **SFA** (Android) — compile sing-box into a Go library via `gomobile bind` and link it into a thin native UI. On iOS the resulting `Libbox.xcframework` is statically linked into a `NEPacketTunnelProvider` extension, with a SwiftUI main app talking to the extension via `NETunnelProviderSession`. On Android the same core becomes `libbox.aar`, consumed by a Kotlin `VpnService` implementation. Binary sizes land around 30–40 MB on Android and similar on iOS — about one-third the size of the equivalent Flutter-based Hiddify builds.

**Hiddify is the instructive counterexample**. It uses the same sing-box core but wraps it in Flutter for "one UI across five platforms". The result is Android APKs of **114 MB (arm64), 102 MB (armv7), 324 MB (universal)**, and an iOS App Store listing of 174 MB. Most of that bulk is sing-box plus geoip/geosite databases, but Flutter adds a measurable 20–30 MB engine on top of every platform. For a user in Iran on a 4 GB/month cellular plan, downloading a 114 MB anti-censorship client from a GitHub release page over an already-constrained connection is a real barrier. Hiddify's UX is excellent and its iOS NE integration is proven — we'll steal the shape of its gomobile bindings and URL-scheme handlers — but its UI stack is the wrong trade-off for our priorities.

**Outline Client** demonstrates the alternative "pure native" extreme: `outline-go-tun2socks` + `outline-sdk` as the Go core, Swift/Obj-C on Apple, Kotlin on Android, Electron + Go-sidecar-subprocess on Windows/Linux. It achieves a 31.7 MB iOS IPA and a 46 MB Android APK, the smallest of any serious multi-platform client surveyed. The cost is four UI codebases and an Electron desktop client that weighs in at ~90 MB — the one blemish on an otherwise exemplary architecture.

**Clash Verge Rev** is the desktop answer. It's a Tauri 2 application (Rust backend + WebView2/WKWebView/WebKitGTK frontend + React UI) that bundles **mihomo as a sidecar binary**. Tauri's Rust build layer downloads the correct mihomo binary per target triple at build time and ships it as a resource; at runtime, the Rust backend spawns mihomo as a child process and talks to it over the Clash RESTful API. A Windows service/launchd/systemd unit runs the core elevated for TUN mode while the GUI stays unprivileged. Installer sizes are **15–25 MB** on Windows (no bundled WebView2), ~20 MB DMG on macOS, ~25 MB .deb/.rpm/.AppImage on Linux — roughly a sixth the size of Electron-based equivalents. Nyanpasu and Mihomo Party use the same pattern. This is the template for our desktop client.

**NekoBox-for-Android** is the template for Android: Kotlin + Jetpack Compose + VpnService + `libbox.aar` (gomobile-bound sing-box) with an optional plugin-APK mechanism (inherited from shadowsocks-android) for protocols the embedded core doesn't cover, like Trojan-Go or NaiveProxy. ~50 MB APK. **v2rayNG** is a viable fallback model (older Android Views UI) and its intent-handling and subscription parsing code are battle-tested against every URI format Iranian providers emit.

The other patterns are explicitly worth *not* copying. Nekoray desktop (Qt + Go sidecar) was elegant but is now archived; Qt's licensing and deployment bulk were never worth the savings. FLClash (Flutter + mihomo FFI) has no official iOS build because its maintainer cannot obtain an Apple Developer account — a structural problem for any Iran-origin project and a warning about Apple distribution. Electron for desktop is immediately disqualified on size.

## UI strategy — native mobile, Tauri desktop, nothing unified

For a Go-core client with strict size priorities, neither the "unified Flutter everywhere" nor the "pure native Outline" approach is optimal. The right answer is a **hybrid**: native Swift/Kotlin on mobile, Tauri 2 on desktop.

On mobile, the native path costs one extra UI codebase (Swift + SwiftUI for iOS/macOS, Kotlin + Compose for Android) but saves 20–30 MB per bundle and — critically — keeps the iOS Network Extension process lean. This matters more than it sounds. iOS's `NEPacketTunnelProvider` extension has a **hard ~50 MB memory ceiling on iOS 15+** (it was 15 MB before, and there are credible reports on Apple DevForums thread 747474 that some iOS 17 devices still enforce ~15 MB in practice). Sing-box's own issue tracker documents the extension being jetsam-killed during high-throughput WireGuard transfers or geosite/geoip loading. Adding a Flutter or Compose-Multiplatform renderer into the same process or the main app reduces your headroom — even though the UI lives in the main app, the shared Go runtime memory accounting can be tight. Native UIs keep the NE process as a bare Swift target linked against the Go XCFramework, nothing else.

On desktop, **Tauri 2** beats everything. It ships a 3–10 MB installer (claimed minimum 600 KB, typical 5 MB after release optimizations), uses the OS's native WebView, and has first-class support for bundling "sidecar" binaries. A single Rust/TS codebase produces Windows, macOS, and Linux packages. Native Win32 or WinUI would be smaller still but would force a second desktop UI codebase for macOS and a third for Linux. GTK/Qt adds 30–60 MB of runtime libraries. Flutter Desktop is proven (Hiddify uses it) but ships 40–60 MB Linux AppImages versus Tauri's 25 MB. Electron is ~100 MB. .NET MAUI has no Linux target. Compose Multiplatform for desktop still boots a JVM. Tauri is the Pareto point.

The one tricky seam is **how Tauri talks to sing-box on desktop**. Two options exist: spawn sing-box as a sidecar subprocess (what Clash Verge Rev does) and drive it over its clash-compatible RESTful API; or compile sing-box with `go build -buildmode=c-shared` into a `.dll`/`.so`/`.dylib` and load it from Rust via `libloading`. The sidecar approach is dramatically simpler, cleaner on license boundaries (sing-box is GPLv3; keeping it as a separate process avoids linking arguments), and mirrors the desktop pattern Outline already ships. Use it. Reserve the `c-shared` option for the iOS/macOS tunnel extension where subprocesses are forbidden — there, link sing-box as a static XCFramework just like SFI does.

The frameworks explicitly rejected and why: **Flutter**, because the 20+ MB engine overhead multiplies across three desktop OSes plus two mobile targets, and Iranian users on metered plans feel each megabyte. Hiddify proves it *works* but the 114 MB Android APK is evidence of the cost. **Qt/QML**, because of deployment bulk and LGPLv3 complications for a redistributable tool. **React Native**, because the desktop story is weak (no Linux, RN-Windows and RN-macOS are second-class) and the iOS/Android size is worse than Flutter's on most metrics. **Compose Multiplatform**, because desktop JVM bundles are 40–80 MB and iOS Skia overhead still adds ~9–25 MB while providing nothing Kotlin/Compose-Android doesn't already. **.NET MAUI**, because no Linux. **Electron**, by the rules of the brief.

## iOS is the pinch point, and the constraint is sanctions, not memory

Every architecture decision for a multi-platform client gets dominated by iOS, and for a client targeting Iran it's dominated twice. The technical constraints are well-known: a `NEPacketTunnelProvider` extension, the entitlement `com.apple.developer.networking.networkextension` with `packet-tunnel-provider` value (requires Apple review and sometimes refusal for non-commercial apps), **static linking only, no subprocesses, no JIT, no dynamic code loading**, and the memory ceiling described above. The pattern that works — and that sing-box, Hiddify, Outline, Psiphon, Lantern, Streisand, FoXray, and Shadowrocket all implement — is: `gomobile bind -target=ios` produces `Libbox.xcframework` containing a static archive of the Go code with a generated Objective-C header; the Swift main app and the Swift NE extension target both link that framework; the NE extension subclasses `NEPacketTunnelProvider` and hands the TUN file descriptor into the Go core through a thin Swift shim.

The second, harder constraint is distribution. **Apple does not issue Apple Developer Program accounts to Iranian developers** under OFAC sanctions; this has been the rule for years and was reinforced by the 2019 enterprise-cert revocations that killed dozens of Iranian apps overnight. Any iOS path must rely on a non-Iran-based legal entity holding the developer account. From there, three viable distribution channels exist, in descending order of reach:

App Store distribution is the most accessible for end users but subjects a VPN app to content review, and Apple has precedent for region-restricting or removing apps when states formally request it (China, Russia, UAE). TestFlight is the Hiddify playbook: **10,000 users per build, 90-day expiry, no sideload redistribution**. Hiddify explicitly refused to ship sideloadable IPAs after their bundle-group identifiers changed (discussion #1135), because re-signing broke the Network Extension's app-group IPC. Plan your bundle identifiers and entitlement sharing so that third-party re-signing (AltStore, Sideloadly) doesn't break the tunnel — this is a one-time design decision with permanent consequences. Personal Apple IDs give users 7-day free re-signing, which is acceptable for activists but miserable for the general public.

The implication for architecture is that **iOS must be designed as a constrained target from day one**, not adapted from a desktop-first codebase. That means: strict Go build tags to trim sing-box to essentials for the iOS build (drop V2Ray stats API, drop unused transports, keep geosite/geoip minimal); optional separation of WireGuard into boringtun to save memory; and an explicit UI flow where the heavy work (profile editing, rule-set management, diagnostics) lives in the main app rather than the extension.

## Android packaging, desktop packaging, and the binary-size discipline

Android is the easy platform. `VpnService` has no memory limits comparable to iOS, direct APK sideloading is the dominant distribution mode in Iran (Google Play is blocked and its VPN policies are hostile anyway), and F-Droid provides an OSS-build alternative for trust-sensitive users. The rules are standard: build split APKs per ABI (arm64-v8a + armeabi-v7a is enough; x86_64 only for emulator users), use App Bundles if publishing to any store, apply R8 shrinking plus `shrinkResources` plus `resConfigs` to trim locales you don't ship, and call the Go core via `gomobile bind` (producing an AAR with per-ABI `.so`) or via `CGO_ENABLED=1 go build -buildmode=c-shared` + hand-written JNI for finer control and smaller output. `minSdk 24` (Android 7.0) is the sensible floor. Target APK sizes should be **40–50 MB per ABI**, matching NekoBox and v2rayNG; anything over 70 MB means the engine wasn't trimmed.

Windows has one real decision and one real risk. The decision is **WinTUN over TAP-Windows** — WinTUN is the modern, signed, WireGuard-project-maintained TUN driver distributed as a single `wintun.dll`, used by sing-box, Tailscale, and every modern VPN client. The risk is **SmartScreen**. An unsigned `.exe` will generate a "Windows protected your PC" warning on first run; a fresh OV code-signing certificate ($75–$200/year) needs weeks-to-months of install reputation to clear this; an EV cert ($200–$500/year) gives immediate reputation. For an anti-censorship tool paid for by donations or grants, budget for an EV cert or accept the warning and document the workaround. Ship three Windows artifacts: an NSIS setup `.exe` (Tauri's default), an MSI for enterprise, and a portable ZIP — the portable variant matters because non-technical users share files on USB sticks, and a zero-install tool skips SmartScreen entirely.

macOS is about Gatekeeper. Ship a Developer-ID-signed, notarized, universal (`lipo`-merged arm64 + x86_64) `.app` bundle inside a DMG, using a System Extension for the packet tunnel (no 50 MB memory cap unlike iOS). For Linux, ship a static `musl`-linked binary inside an AppImage (~25 MB) plus a small `.deb` and `.rpm`; use a setuid-zero privileged helper or a systemd unit to open `/dev/net/tun` and pass the descriptor to the unprivileged GUI over a Unix socket. Avoid Flatpak and Snap — both have TUN/Wayland portal limitations that bite VPN apps.

A universal rule across platforms: **do not UPX-compress signed binaries**. UPX breaks macOS notarization, iOS signing, Windows SmartScreen reputation, and Play App Signing verification, and triggers many AV heuristics. The 30–50% size savings on paper are not available in practice.

## Offline bootstrap — the feature that actually wins users

Iranian users already have a working anti-censorship ecosystem built around Telegram-channel distribution of V2Ray/VLESS-Reality/Hysteria2 subscription URLs sold by small paid providers or posted by free-config aggregators. The client's job is not to replace this, but to **accept every format those channels emit and degrade gracefully when the channel itself is blocked**. Ten formats matter, ordered by prevalence in the Iranian market:

The universal envelope is the **base64-encoded multi-line subscription**: an HTTPS URL returns a base64 blob that decodes to one URI per line, mixed `vless://`, `vmess://`, `trojan://`, `ss://`, `hysteria2://`, `tuic://`. Every serious Iranian provider publishes this. Response headers carry metadata (`subscription-userinfo`, `profile-update-interval`, `profile-title`, `support-url`, Hiddify's `moved-permanently-to`). The individual URIs are de-facto standards documented in project wikis rather than RFCs: `ss://` per SIP002 with AEAD-2022 plain-text fallback, `vless://uuid@host:port?params#name` with Reality extensions `pbk`/`sid`/`spx` and `flow=xtls-rprx-vision`, `vmess://` as base64-encoded JSON per 2dust's wiki, `trojan://` per trojan-gfw, `hysteria2://` or `hy2://` (accept both) per apernet's URI scheme, `tuic://uuid:password@host:port?params` per sing-box's convention. Above these, accept **sing-box JSON profiles**, **Clash/mihomo YAML subscriptions** (the typical "three URLs side-by-side" that Iranian vendors ship: v2rayN base64 + Clash YAML + sing-box JSON), **SIP008 JSON** for Outline compatibility, WireGuard `.conf` (including AmneziaWG's `Jc/Jmin/Jmax/H1..H4` Iran-specific DPI-evasion extensions), and plain Tor bridge lines. Internally, convert everything to sing-box outbound JSON — it is the only format that natively expresses every protocol on the list.

For out-of-band delivery the right set, in priority order: **static QR code** of a short URI or sublink URL (≤ 900 bytes fits a Version 20 QR reliably); **clipboard auto-detect** on app foreground (Iranians copy links from Telegram every day); **file import** via system share sheet, document picker, and Android intent filters for `.json/.yaml/.conf/.ovpn/.txt`; **local Wi-Fi + mDNS peer-to-peer share** with self-signed TLS, fingerprint pinning, and a 6-digit PIN, modeled on LocalSend plus Briar's two-QR handshake; **animated fountain-coded QR** (using Luby Transform codes, following the txqr design at ~8–12 FPS) for medium payloads up to ~10 KB when no network is available; **USB sneakernet** with a portable single-folder build (app binary + `profiles/` directory + a signed manifest); Android Nearby Connections and iOS MultipeerConnectivity as opportunistic same-OS optimizations; and Bluetooth pair-by-QR as a last resort. Cross-OS Bluetooth remains unreliable (Google's Nearby iOS support is still discussion #2447 territory), so Bluetooth should be an Android-to-Android and iOS-to-iOS feature rather than an interoperability promise.

The **signed-manifest bundle** is the feature almost no existing project has and every Iranian user needs. Define a `.sbp` archive (zip of `manifest.json + manifest.sig + publisher.pub + profiles/*`) signed with an ed25519 publisher key. On receive, verify the signature, show the publisher's 4-word BIP-39 fingerprint, apply TOFU trust, and pin the key to the author's display name so subsequent shares from the same publisher skip confirmation. This is the only thing that makes "my friend sent me configs on a USB stick" safe against the obvious man-in-the-middle attacks. Psiphon's `ServerEntrySignaturePublicKey` is the proof-of-concept; extend it to user-facing bundles.

Finally, a **hybrid bootstrap** layer modeled on Psiphon/Lantern: bake 20–30 signed bootstrap server entries into the app binary, covering Shadowsocks + VLESS-Reality + Hysteria2 with at least two domain-fronted transports. On first launch with zero user profiles, connection-race them in parallel. Connect the user to *something*, even if rate-limited, and then prompt: "You're on the shared bootstrap pool — import a real subscription for full speed." This solves the chicken-and-egg problem that kills the sub-import-only model the moment Iran blocks Cloudflare Workers or the user's Telegram channel. Refresh the bootstrap list periodically over the tunnel itself, Psiphon-style, with ed25519-signed delta updates. Run this as a tiny, shared, rate-limited service and label it honestly; the goal is to buy the user the five minutes they need to fetch a real sublink, not to provide bulk VPN service.

## The recommended stack, end to end

| Layer | Technology | Rationale |
|---|---|---|
| Protocol engine | **sing-box** (Go library, not CLI) + vendored Psiphon + Snowflake + obfs4 + Cloak + Lantern transports | Only ecosystem that covers all required protocols; actively maintained against Iranian DPI |
| Optional sub-engine | **boringtun** (Rust) for WireGuard on iOS if NE memory pressures it | ~1.5 MB vs ~5 MB for wireguard-go, keeps headroom |
| Core packaging | `gomobile bind` → XCFramework + AAR for mobile; `go build -buildmode=c-archive` for iOS NE direct linking; prebuilt sing-box binary as Tauri sidecar for desktop | Matches sing-box-for-apple + Clash Verge Rev patterns |

| iOS/macOS UI | SwiftUI, shared code between the two, separate `NEPacketTunnelProvider` target statically linking the Go XCFramework | Mirrors SFI/SFM; fits NE memory budget |

| Config manager | Sing-box JSON as internal representation; parsers for base64-sublink, vless/vmess/trojan/ss/hy2/tuic URIs, SIP008, Clash YAML, WireGuard `.conf`, AmneziaWG, Tor bridge lines | Interoperates with every Iranian provider |

### Module architecture in prose

Picture five layers talking through narrow interfaces. The **engine layer** is `libengine`, a cgo-produced artifact of sing-box plus extra Go transports, exposing a flat C ABI of about a dozen functions: start a tunnel given a config JSON, stop it, query live stats, register an event callback, rotate profiles, update routing. It is identical on every platform. Above it sits a thin **platform bridge**: Swift on Apple, Kotlin JNI on Android, Rust `tauri::command` handlers on desktop. The bridge converts platform-native calls (Swift struct, Kotlin data class, JSON from the webview) into C calls and back, and owns the platform lifecycle (Network Extension startTunnel/stopTunnel, VpnService onStartCommand, Tauri window events).

Above the bridge lives the **config and subscription manager**, a module that parses every URI format, normalizes to sing-box JSON, maintains a local profile database (SQLite on all platforms), fetches subscription URLs with graceful retry-over-tunnel fallback, and emits "profile updated" events the UI observes. It is written twice — once in Swift/Kotlin for mobile, once in Rust for Tauri desktop — because sharing it across languages would force Flutter, and the rest of this report rejected that trade. The duplication is small (a few thousand lines) and contained.

At the top sits the **UI layer**: SwiftUI views on iOS/macOS, Compose on Android, a React + Tailwind single-page app rendered in the Tauri webview on desktop. All three consume the same logical view model — connection state, profile list, traffic stats, rule editor — which the config manager populates. The main app communicates with the tunnel process (extension on iOS, VpnService on Android, sidecar on desktop) through platform-native IPC: NETunnelProviderSession messages, Binder, named pipe / Unix socket respectively.

The **offline-share module** cuts across all of the above. It exposes a "share" action that the UI invokes, a "receive" handler wired to the system Share Sheet on iOS/Android, a drag-drop target on desktop, and an always-on mDNS browser when the user is on the "receive via LAN" screen. Sends build a signed `.sbp` bundle, spin up an ephemeral HTTPS server on a random port with a self-signed cert and a PIN, and advertise `_vpnshare._tcp.local.`. Receives pull the bundle, verify the ed25519 signature against a TOFU-pinned publisher key, and hand the parsed profiles to the subscription manager. QR generation and fountain-coded animated QR live here too, using `go-qrcode` + a port of `divan/txqr`'s LT codec cross-compiled to each platform via the same cgo bridge.

The **bootstrap module** ships a compiled-in signed list of bootstrap server entries, a tiny connection-racing engine that tries them in parallel on first launch, and a background refresher that pulls list updates through whichever tunnel is currently up. It presents itself to the UI as just another profile source — distinguished by a visual badge — so the user always sees the distinction between "shared bootstrap" and "your subscription."

## Trade-offs worth stating honestly

This stack costs you one extra UI codebase vs. Hiddify (two mobile UIs + one desktop UI instead of a single Flutter codebase), roughly 30% more initial engineering. In exchange you ship 50–70 MB smaller mobile bundles, 25–40 MB smaller desktop installers, better iOS memory headroom, better per-platform UX polish, and easier independence from any single framework's upstream decisions. For an anti-censorship tool whose users weigh every megabyte of mobile data, the trade favors native mobile decisively.

The Go-core decision costs you startup time and runtime memory vs. a Rust core. Expect ~200–500 ms cold starts on Android mobile devices, ~30–80 MB idle RSS, and occasional iOS NE jetsam kills under sustained high-throughput WireGuard loads. These are known issues with known partial mitigations (build-tag trimming, boringtun sub-engine, lazy geoip loading) and they are the price of protocol coverage. Moving to Rust gives back ~15–20 MB of binary, halves memory, and buys you effectively nothing in protocols because the critical ones — Reality, Hysteria2, Psiphon, Snowflake, Cloak — do not exist in Rust today, and will not in any timeframe that matters.

The Tauri desktop decision bets on a still-maturing framework (v2.0 stable shipped October 2024, mobile support is stable but its plugin ecosystem lags desktop by 12–18 months). Clash Verge Rev, Nyanpasu, and Mihomo Party have already validated the desktop pattern at scale, which mitigates the bet. Do not use Tauri mobile yet — native Swift and Kotlin remain safer on iOS and Android.

The biggest non-technical trade-off is iOS. Apple's sanctions policy means the iOS build cannot be maintained from inside Iran, the App Store listing will be vulnerable to geo-takedown at any moment, and no sideload path works reliably for users without foreign payment methods. The only mitigation is to treat iOS as a channel that must be kept working by a non-Iranian legal entity (a foreign NGO, foundation, or partner vendor) and to design bundle identifiers and Network Extension entitlements so that TestFlight and occasional AltStore re-signing survive. This is a political problem in a technical disguise; no architecture choice solves it.

## Conclusion — what this exercise actually established

The surprising result of this research is not which stack to pick but **how tightly the protocol ecosystem forces the language choice, which forces the core library choice, which forces the FFI and packaging approach, which forces everything else**. sing-box is not merely the best available engine; it is the load-bearing wall of the Iranian circumvention market, and any new client that doesn't embed it is either reinventing two years of work or accepting inferior DPI-resistance against one of the world's most adversarial state censors. Once you accept sing-box, the rest of the stack — gomobile bindings, Tauri desktop with Go sidecar, native mobile UIs, sing-box JSON as internal representation — follows by a short chain of deduction that every successful project in this space has already walked.

The one thing those successful projects have not yet solved is bootstrap resilience under complete blackout. Hiddify's subscription import assumes the user can reach Telegram. Outline's access keys assume the admin can hand out URLs. Psiphon's embedded server list is the best existing answer but is vendor-tied. A new entrant has a real opportunity to treat **offline share, signed peer-to-peer bundles, and hybrid bootstrap** as first-class features rather than afterthoughts. The ~500 lines of code that make up a fountain-coded animated QR plus an mDNS-advertised HTTPS server plus an ed25519-signed bundle format are a smaller investment than the UI layer and a much larger user win under the actual conditions Iranians face during protest-related shutdowns. Build the engine on sing-box; build the rest on the assumption that the internet will not be there when your users need it most.
